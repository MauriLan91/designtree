DesignTree user guide

Introduction

DesignTree is a graphical editor for Linux devicetrees. Instead of writing .dts files by hand, you place nodes on a canvas, wire them together and group them, in the style of node editors such as n8n or Simulink. The result is ordinary devicetree source in kernel style, and a .dtb built with dtc.

The element library is not bundled: it is built from the binding schemas (Documentation/devicetree/bindings) of a Linux kernel checkout on your machine, so it always matches the kernel you target.

On the canvasIn the devicetree
NodeA node (serial@10000000) with its compatible strings and properties
Child edge (bottom to top handle)The parent/child relation
Reference edge (right to left handle)A phandle property, such as clocks = <&osc24m>;
GroupVisual grouping only, like a Simulink subsystem; no effect on the output

DesignTree is made for two kinds of work:

  • Board bring-up: start from a SoC .dtsi of the kernel and describe what your board adds, with the board view next to the schematic.
  • BSP maintenance: open existing board files, change them on the canvas or in the text, and export them with small diffs: the includes stay, and your changes become &label { } overrides.

Design files are JSON (.json). They hold the tree, the canvas layout, the board view and the kernel version the design was built against. Devicetree source is an export, not the file you save.

Installing DesignTree

DesignTree is packaged for Linux first. Arch Linux and its derivatives (Manjaro, EndeavourOS) build it from a PKGBUILD; other distributions use the AppImage or the .deb attached to each GitHub release. Windows and macOS installers are not built yet; build from source there.

Every package installs the desktop app (designtree-app, with a menu entry) and needs dtc for Build .dtb. The Arch package also installs the designtree command line.

Arch Linux and Manjaro

Two PKGBUILDs live in packaging/arch/:

PackageBuildsUse it for
designtreethe tagged release (v<version> tarball)normal use
designtree-gitthe latest commit on maintrying unreleased work

Build and install either with makepkg, from a clone of the repository:

git clone https://github.com/MauriLan91/designtree.git
cd designtree/packaging/arch/designtree-git    # or designtree, once a release is tagged
makepkg -si

makepkg -s installs the build dependencies (cargo, nodejs, npm) with pacman. The build takes a few minutes; check() runs the core and bindings test suites. Remove the package with sudo pacman -R designtree-git.

The PKGBUILD attached to each release already carries the tarball checksum and is the file published to the AUR (see Publishing to the AUR).

Wayland and NVIDIA

On some Wayland sessions, KDE Plasma with an NVIDIA GPU among them, WebKitGTK’s DMA-BUF renderer closes the window at start with Error 71 (Protocol error) dispatching to Wayland display. DesignTree sets WEBKIT_DISABLE_DMABUF_RENDERER=1 for itself on Linux, so no setup is needed. To try the DMA-BUF renderer anyway, start it with WEBKIT_DISABLE_DMABUF_RENDERER=0 designtree-app.

AppImage

chmod +x DesignTree_<version>_amd64.AppImage
./DesignTree_<version>_amd64.AppImage

Install dtc from your distribution (device-tree-compiler on Debian and Ubuntu) to build .dtb files. The AppImage is built on Ubuntu 22.04 and runs on distributions with glibc 2.35 or newer.

Debian and Ubuntu

sudo apt install ./DesignTree_<version>_amd64.deb

The package depends on device-tree-compiler and the WebKitGTK 4.1 runtime (Ubuntu 22.04, Debian 12 or newer).

Verifying a download

Each release has a SHA256SUMS file: sha256sum -c SHA256SUMS --ignore-missing checks what you downloaded. The packages also carry a signed build provenance attestation that ties the file to the release workflow run that built it from this repository:

gh attestation verify DesignTree_<version>_amd64.AppImage --repo MauriLan91/designtree

Updates

Once a day at start, DesignTree asks GitHub for the latest published release (one request to api.github.com, nothing else is sent). When it is newer than the running version, a bar at the bottom says so and how to update for the way it was installed: the AUR helper or PKGBUILD on Arch, a new .deb or AppImage elsewhere. The app does not replace itself; on Arch the package manager stays in charge. Don’t check in the bar turns the check off; Check for updates now in the command palette (Ctrl+K) checks at once and turns it back on.

First start: a kernel checkout

The element library comes only from the binding schemas of a Linux kernel checkout on your machine. Without one, the canvas works but the library is empty and schema checks are off. A sparse checkout of the parts DesignTree reads is enough:

scripts/fetch-kernel-dts.sh ~/linux        # from the repository; tag v7.3 by default

or by hand:

git clone --depth 1 --filter=blob:none --sparse https://github.com/torvalds/linux.git ~/linux
git -C ~/linux sparse-checkout set Documentation/devicetree/bindings \
    arch/arm/boot/dts arch/arm64/boot/dts include/dt-bindings include/uapi/linux \
    scripts/dtc/include-prefixes

Then press Kernels… in the toolbar, Add checkout…, pick ~/linux and Use. DesignTree remembers the checkouts you add. DESIGNTREE_LINUX_SRC=~/linux designtree-app loads one at start instead.

From source

Needs Rust 1.90 or newer, Node.js 20 or newer, dtc and the WebKitGTK 4.1 development files (Arch: webkit2gtk-4.1; Debian/Ubuntu: libwebkit2gtk-4.1-dev libgtk-3-dev librsvg2-dev).

cd app
npm ci
npx tauri build --no-bundle               # target/release/designtree-app
cargo build --release -p designtree-cli   # target/release/designtree

packaging/linux/install.sh <destdir> installs both with the desktop entry, icons and AppStream metadata, for distribution packages.

Publishing to the AUR

For the maintainer, after a release is published:

git clone ssh://aur@aur.archlinux.org/designtree.git aur-designtree
cd aur-designtree
cp ~/Downloads/PKGBUILD .                      # from the release assets
cp ~/Downloads/designtree.SRCINFO .SRCINFO
git add PKGBUILD .SRCINFO
git commit -m "Update to <version>" && git push

designtree-git is published the same way from packaging/arch/designtree-git (makepkg --printsrcinfo > .SRCINFO), once; it rebuilds from main on every install.

Tutorial: your first board

This tutorial builds a minimal board from an empty canvas to a .dtb: a CPU, memory, a clock, an interrupt controller with a UART, and an LED on a GPIO. It takes about 15 minutes. Each step ends with a checkpoint design in examples/ (installed in /usr/share/designtree/examples by the Arch package); open it with Open… to compare, or to start from that step.

You need a kernel checkout loaded under Kernels… (see Kernel checkouts) and dtc installed.

Properties that have no field of their own go in the inspector’s Properties box, one name = value per line (reg = <0x40000000 0x20000000>), or straight into the DTS source panel.

Nodes the kernel’s schemas do not describe (cpus, memory, chosen, aliases, the LED itself) are added with + Empty node and named in the inspector. Everything else comes from the library search.

1. The root and the CPU

  1. New (Ctrl+N). Select the root node /.
  2. In the inspector, set Compatible to acme,first-board and add model = "Acme First Board" to its properties. The root already has #address-cells = <1> and #size-cells = <1>.
  3. + Empty node, name it cpus, and wire it under the root (root’s bottom handle to its top handle). Give it #address-cells = <1> and #size-cells = <0>.
  4. Search the library for cortex-a7 and add the CPU. Wire it under cpus, name it cpu with unit address 0, and set device_type = "cpu" and reg = <0>.

Checkpoint: first-board-1-cpu.json.

2. Memory

  1. + Empty node under the root, named memory.
  2. Set the unit address to 40000000, and the properties device_type = "memory" and reg = <0x40000000 0x20000000> (512 MiB at 0x40000000).

Checkpoint: first-board-2-memory.json.

3. A clock

  1. Search for fixed-clock and add it under the root, named oscillator with the label osc24m.
  2. Its required properties come pre-filled: set clock-frequency to 24000000 and keep #clock-cells = <0>.

Checkpoint: first-board-3-clock.json.

4. Interrupt controller and UART

  1. Search for cortex-a7-gic, add it under the root as interrupt-controller@1c81000 with the label gic. Set reg = <0x01c81000 0x1000>, <0x01c82000 0x2000> and #interrupt-cells = <3>; interrupt-controller is a toggle.
  2. Search for ns16550a, add it under the root as serial@1c28000 with the label uart0, and set reg = <0x01c28000 0x400>, reg-shift = <2>, reg-io-width = <4>.
  3. Wire the UART’s clocks port to the oscillator, and its interrupt-parent port to the interrupt controller.
  4. Set interrupts = <0 0 4> on the UART: shared peripheral interrupt (GIC_SPI is 0) number 0, level high (IRQ_TYPE_LEVEL_HIGH is 4), the three cells #interrupt-cells asks for.
  5. So that the kernel prints to this UART: add empty nodes aliases with serial0 = &uart0, and chosen with stdout-path = "serial0:115200n8".

Interrupts in the toolbar should now show the UART under gic.

Checkpoint: first-board-4-uart.json.

5. An LED on a GPIO

  1. Search for opencores,gpio, add it under the root as gpio@1c20800 with the label gpio, and set reg = <0x01c20800 0x1>, <0x01c20801 0x1> and reg-names = "dat", "dirout". gpio-controller is a toggle and #gpio-cells is 2.
  2. Search for gpio-leds and add it under the root, named leds.
  3. + Empty node under leds, named led-0, with default-state = "off".
  4. Wire the LED’s right handle to the GPIO controller: the property becomes gpios. Click the new edge and, in the specifier editor, set line 0 and pick GPIO_ACTIVE_HIGH (the names come from the kernel’s dt-bindings headers).

Checkpoint: first-board-5-led.json.

6. Check and build

  • The Schema check panel should be empty. If it lists something, click the problem to jump to the node, and compare with the checkpoint.
  • Address map shows the four devices on the root bus with no overlaps.
  • Save… the design, then Build .dtb (Ctrl+B): board.dtb appears next to board.json, and the Build panel shows no warnings.

You have a devicetree that the kernel can boot with. From here, try Board view to place the devices on a photo of your board, or Export .dts… to see the source in kernel style.

The window

  • Tabs at the top hold the open designs. A dot marks unsaved changes; closing a tab or the window with unsaved changes asks first.
  • Toolbar: New, New from SoC…, New overlay…, Open…, Import .dts…, Save…, Export .dts…, Build .dtb, Kernels…, dtc path…, and the views Interrupts, Address map and Board view. The second row has Commands… (the command palette), Undo, Redo, Auto layout, Group and Ungroup.
  • Library (left): the elements of the loaded kernel checkout, with search, categories, favorites and recent elements.
  • Canvas (middle): the devicetree as a graph. Zoom with the mouse wheel or the buttons at the bottom left; the minimap at the bottom right shows where you are.
  • Inspector (right, top): the selected node, reference or group.
  • DTS source (right, bottom): the devicetree source of the design, editable, kept in sync with the canvas. Under it, the Schema check and Build panels list problems when there are any.

To open a design at start, pass its path: designtree-app board.json.

Kernel checkouts and the library

The library lists every device the kernel’s binding schemas describe: thousands of schemas and tens of thousands of compatible strings. It comes only from a kernel checkout on your machine (see First start for a sparse one).

Adding a checkout

Press Kernels…, then Add checkout… and pick the top directory of the kernel tree. The list shows each checkout with its version, read from the kernel’s Makefile. Use loads one; the first index of a checkout takes a few seconds and is cached, so the next start is fast. The cache is rebuilt when the bindings change. Load kernel bindings… in the library does the same for a checkout not in the list yet.

The design records the kernel version it was built against. Opening it while a different version is loaded shows a warning above the canvas, because bindings may differ between kernels.

Finding an element

Type in the search box: the search is fuzzy over the compatible string, the vendor and the schema title, ranked by match quality, so bme280, bosch pressure and i2c eeprom all work. Narrow it with the category list. The star next to an element adds it to Favorites; elements you add show up under Recent. Both are kept between sessions.

Adding a node

Click an element, or drag it to the canvas. The new node comes with its compatible, a reg placeholder, status = "okay" and the properties its schema requires, filled with defaults where the schema has them. Properties that still need a value are marked as to-do in the inspector.

+ Empty node adds a node without a compatible, for nodes the schemas do not describe (chosen, aliases, memory).

Building a design

New (Ctrl+N) starts an empty design with a root node /. Everything else hangs below it.

Nodes and the tree

Each node shows its label and name (uart0: serial@10000000), its first compatible string and how many properties it has. To put a node under another one, drag from the parent’s bottom handle to the child’s top handle; a node has one parent. Move selected node under… in the command palette does the same from the keyboard.

References

Phandle properties are edges from the consumer’s right handle to the provider’s left handle. When the schemas know the node, its handles are named ports: a UART shows clocks, a clock controller clock, a GPIO controller gpio. Only matching ports connect, and the edge writes the property (clocks = <&osc24m>;), with as many specifier cells as the provider’s #clock-cells asks for. Without a schema, the property name is guessed from the target’s #…-cells and can be edited in the inspector.

Click an edge to edit it in the inspector: the property name, and the specifier cells with names from the kernel’s dt-bindings headers, such as GPIO_ACTIVE_LOW or IRQ_TYPE_LEVEL_HIGH.

Groups

Select nodes (Shift+drag selects an area) and press Group (Ctrl+G) to frame them, for example “SoC peripherals”. Groups are only visual and never reach the devicetree. The triangle in a group’s header collapses it into a block, like a Simulink subsystem: edges that cross its border become ports on the block. Ungroup (Ctrl+Shift+G) removes the frame.

Layout

Auto layout (Ctrl+L) arranges the tree from the root down, with a group for each bus. Imported designs are laid out on import. Positions are saved in the design file.

Saving

Save… (Ctrl+S) writes the design file (.json). Export .dts… writes the devicetree source: kernel style, tabs, a blank line between properties and subnodes, imported nodes in their original order.

The inspector

Select a node to edit it in the inspector.

  • Name, Unit address, Label and Compatible (comma separated) come first.
  • Binding properties: with a kernel checkout loaded, the properties of the node’s schema, required ones first and marked with *. Each has an input for its type: a dropdown for an enum, a toggle for a boolean, a number list for a cell array, text for strings. Hover a property for the schema’s description. Required properties without a value are marked as to-do.
  • Other properties (or Properties without a schema): anything the schema does not describe stays editable as raw devicetree values, so nothing is lost.

Select a reference edge to change its property name and specifier cells; select a group to rename it.

Inherited nodes

After importing a board file, nodes defined in an included .dtsi have a dashed border and show the file they come from. They are read-only so that an accidental edit does not change the SoC: press Override to edit one. Its changes are exported as a &label { } block in your board file, and deleting it exports /delete-node/. Inherited nodes cannot move to another parent.

Importing board files

Import .dts… opens existing devicetree source: a kernel board file, a vendor BSP file or anything dtc accepts.

  • #include of .dtsi files and dt-bindings headers is resolved, and C macros such as GPIO_ACTIVE_LOW and IRQ_TYPE_LEVEL_HIGH are expanded. Inside a kernel tree the kernel’s include directories are found automatically.
  • For safety, includes are only read from the file’s own directory, its kernel tree and the include directories you configure; nothing else on the disk is opened.
  • Labels, phandle references (&x, <&x 1 2>), /delete-node/, /delete-property/ and &label { } overrides are all understood. References become reference edges.
  • Parse errors show the file, line and column.

Board files stay board files

A board file that includes a SoC .dtsi is kept as one. The included nodes appear as inherited, and exporting writes the same includes followed by only your board’s changes as overrides. An unmodified import compiles to the same .dtb as the original, and the text stays close to it, so your diffs stay small.

When a file cannot be layered (an include inside a node, or after the board nodes), the design is imported flat instead.

Boards from a SoC and overlays

New board from a SoC

New from SoC… lists the SoC .dtsi files of the loaded kernel tree, filterable by architecture and vendor. Pick one and the new design includes it: the SoC’s nodes are inherited, and you only add and override what your board has, as in a kernel board file.

Overlays

New overlay… starts an overlay (.dtso) against a base: a design file or a board .dts. Every node of the base is inherited. Add nodes and override base nodes as usual; the export is /plugin/ source with one &label { } fragment per changed node, and Build .dtb produces a .dtbo.

The DTS source panel switches between Overlay, the overlay source, and Applied, the base with the overlay applied, to check the result. Some changes cannot be expressed by an overlay (deleting a base node, for example); they are reported as problems. The overlay’s source is read-only in the editor.

Editing the DTS source

The DTS source panel shows the design as devicetree source, with syntax highlighting, and you can edit it. A short pause after you type, the text is parsed and the canvas follows; edits on the canvas update the text. Nodes keep their place on the canvas when you change them in the text.

Selection follows both ways: selecting a node scrolls the text to it, and moving the cursor into a node’s block selects the node. While the text does not parse, the error is shown and the canvas keeps the last valid design.

Checks and problems

DesignTree checks a design at three levels while you edit.

  • Structure: a missing or second root, a node with two parents or none, duplicate labels, references to nodes that do not exist. These block Build .dtb until fixed.
  • Schema check: with a kernel checkout loaded, every node is checked against its binding schemas, like make dtbs_check: required properties, types, enums and constants, properties the schema does not allow, and conditions on the compatible. Problems are marked on the nodes and listed in the Schema check panel.
  • dtc: warnings and errors from building the .dtb (see Building the .dtb).

Click a problem in a panel to select its node on the canvas.

The address map and interrupt views add their own checks: overlapping reg regions and devices with no usable interrupt parent (see Views).

Building the .dtb

Build .dtb (Ctrl+B) compiles the design with dtc. A saved design is built next to its file (board.json → board.dtb, an overlay to .dtbo); an unsaved one asks where to write it.

dtc is taken from PATH. If it is elsewhere, set it with dtc path…, or start the app with DESIGNTREE_DTC=/path/to/dtc. When dtc is missing, the Build panel says so.

The Build panel lists dtc’s errors and warnings. Those about a node are attached to it on the canvas; click one to select the node. dtc runs without a shell and reads the source from standard input.

Views: interrupts, address map, board

Interrupt tree

Interrupts shows each interrupt controller with the devices wired to it, following interrupt-parent, interrupts and interrupts-extended. Devices without an interrupt parent, and interrupt specifiers that do not fit their controller, are flagged.

Address map

Address map shows the reg regions of each bus, translated to CPU addresses through ranges, #address-cells and #size-cells. Overlapping regions and regions outside their bus’s ranges are highlighted.

Board view

Board view is a second canvas over the same design, for where devices sit on the PCB.

  • Background… puts a board photo or a schematic export behind the devices; Clear removes it.
  • Drag devices from Not on the board onto the board and place them as on the PCB. Selection is shared with the graph. Positions are saved in the design file and never reach the devicetree.
  • Connections draws the links between placed devices: I²C and SPI buses, other buses, GPIOs, interrupts and other references, each with its own color and a checkbox to show or hide it. A link to a device that is not placed is drawn to its nearest placed ancestor.
  • Connectors adds pin headers: the 40-pin Raspberry Pi layout, a mikroBUS socket, or a single- or dual-row header with any number of pins. Click a pin to name it, mark it as power or ground, and map it to a SoC pad (a GPIO line or a pinctrl group). Two devices claiming the same pad are flagged as a conflict.

Editing faster

Undo and redo

Every change can be undone: nodes, edges, properties, groups, layout and text edits. Ctrl+Z undoes, Ctrl+Shift+Z or Ctrl+Y redoes, at least 200 steps back.

Copy and paste

Ctrl+C copies the selected nodes with their subtrees; Ctrl+V pastes them under the selected node, also into another tab. Labels are renamed when they would clash, and references between copied nodes are kept.

Tabs

Each design has its own tab with its own undo history. Ctrl+Tab and Ctrl+Shift+Tab switch tabs, Ctrl+W closes one, middle-click closes the tab under the mouse.

Command palette

Commands… or Ctrl+K opens the command palette: type part of a command and press Enter. It has everything in the toolbar plus Add empty node, Connect selected node to…, Move selected node under…, Fit the design in view and Check for updates now.

Command line

The designtree command (installed with the Arch package, or cargo build --release -p designtree-cli) works on the same files as the app, for scripts and CI. designtree <command> --help describes the options.

CommandDoes
import board.dts -o board.jsonImport devicetree source into a design (--linux <tree>, -I <dir> for includes)
export board.jsonWrite devicetree source; a layered import becomes a board file again, --flatten writes the whole tree
validate board.jsonStructural checks
check board.json --linux <tree>Schema check like make dtbs_check; also takes .dts and .dtb
overlay base.json -o overlay.jsonStart an overlay against a design or a .dts
interrupts board.jsonPrint the interrupt tree and its problems
address-map board.jsonPrint the address map, overlaps and unmapped regions
pins board.jsonPrint connector pins and who claims them; fails on a conflict
layout board.json -o board.jsonAuto layout
index <tree> -o catalog.jsonBuild the element library from a kernel tree (--stats for counts)
benchTime the backend on a generated 1,000-node board

A typical CI step for a board kept as a design file:

designtree validate board.json
designtree check board.json --linux ~/linux
designtree export board.json > board.dts
dtc -I dts -O dtb -o board.dtb board.dts

The export of a layered board file still has its #include lines; build it like the kernel does (cpp, then dtc), or export with --flatten.

Troubleshooting

The window closes at start on Wayland with Error 71 (Protocol error). DesignTree turns off WebKitGTK’s DMA-BUF renderer on Linux by itself; if you start it with WEBKIT_DISABLE_DMABUF_RENDERER=0, drop that.

The library is empty. No kernel checkout is loaded: see Kernel checkouts. The checkout needs Documentation/devicetree/bindings.

“Bindings may differ” above the canvas: the design was made against another kernel version than the loaded one. Pick the matching checkout under Kernels…, or carry on and check the Schema check panel.

Build .dtb says dtc is missing. Install it (dtc on Arch, device-tree-compiler on Debian and Ubuntu) or point dtc path… at it.

Build .dtb is greyed out. The design has structural errors; the DTS source panel lists them.

An include is not found when importing. Includes are only read from the file’s directory, its kernel tree and the configured include directories. Import from inside the kernel tree, or pass -I <dir> to designtree import.

The first start with a checkout is slow. Its binding schemas are indexed once and cached; the next start reads the cache.
